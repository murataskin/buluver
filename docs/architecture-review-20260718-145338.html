Problem

DatabaseService is a shallow module exposing SQL statements, raw connections, and 12+ separate database methods, forcing callers to coordinate batch transactions and FTS updates.

Solution

Replace the database-leaking interface with a deep Repository presenting a domain-oriented interface (saveDocuments, search, syncFolderState).

Benefits

  • locality: SQL logic is fully encapsulated
  • leverage: one interface, clean transactions
  • interface shrinks: from 12+ methods to 4
  • locality: FTS indexes update automatically
  • locality: database migration details are hidden

Problem

The thread pool lifecycle, batch task queuing, and UDF parsing logic are exposed directly inside the indexing coordination loop.

Solution

Introduce a deep Parser Pipeline interface that accepts file paths and returns parsed documents, hiding the multithreading details.

Benefits

  • locality: thread lifecycle is fully hidden
  • leverage: single simple asynchronous call
  • testability: swap with synchronous mock parser
  • locality: worker error paths are isolated
  • locality: batching constraints live internally

Problem

Synchronization logic is split, with the scanning loop and watcher callbacks coordinating database writes and FTS updates ad-hoc.

Solution

Unify folder walking, modification diffing, and document pruning under a single Sync Orchestrator.

Benefits

  • locality: sync steps form explicit flow
  • leverage: one place triggers folder updates
  • locality: watching and scanning are unified
  • testability: verify walking without database side-effects
  • interface shrinks: callers trigger sync once
Top Recommendation

1. Consolidate Storage behind a Deep Document Repository

Deepening the database service yields the highest leverage first. By removing raw SQLite leaks (`getDb()`) and consolidating FTS index syncing inside the repository, we clean up the seams before refactoring the sync orchestrator or worker pipeline.
